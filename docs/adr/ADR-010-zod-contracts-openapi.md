# ADR-010 — Shared Zod contracts, error envelope and generated OpenAPI

- Status: Accepted
- Date: 2026-09-26

## Context

The mobile app and the API must agree on shapes and errors, and the API needs documentation that
can't drift from the code.

## Decision

- `@bubo/contracts` (Zod 4) holds:
  - request and response schemas (`healthResponseSchema`, `readyResponseSchema`, …)
  - the route registry `API_ROUTE_DEFINITIONS`
  - the single error envelope
    `{ error: { code, message, requestId, issues? } }`, with stable `ERROR_CODES` and a default
    HTTP status per code
- The API builds payloads typed from the contracts. The mobile client validates every response
  against them.
- `GET /v1/openapi.json` is generated by `buildOpenApiDocument()` using Zod 4's native
  `z.toJSONSchema()` (target OpenAPI 3.0). Every route in the registry is documented.
- Error rules:
  - Clients branch on `code`, never on `message`.
  - Validation issues report the path only, never the submitted secret or value.
- `@bubo/config` validates environment variables with the same library, so values are never
  echoed back.

## Consequences

- Adding a route means adding its contract and registry entry, and the docs follow.
- The same schemas can drive form validation in the app.

## Alternatives considered

- **`@hono/zod-openapi`:** couples routing to the doc generator, and Zod 4 export already covers
  our needs.
- **tRPC:** great in TypeScript, but it hides the HTTP contract, and we want a public REST API.
- **Hand-written OpenAPI:** drifts.
